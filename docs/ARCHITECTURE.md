# RSDP Live! architecture

This is the contract every workstream builds on. Change it only with a note to the other workstreams (see "Changing contracts").

## Layers

```
packages/engine        Pure TypeScript, no I/O. Plays one hand at a time.
  src/core/            Hand state machine, betting structures, forced-bet planner,
                       pots and settlement, events, visibility.      (Workstream 0)
  src/variants/        Game specs, evaluators, awardPortion, stud and draw helpers. (W3)
  src/modifiers/       Bomb pot, double board, 7-2 bounty, nit game, rake.        (W2)
packages/tournament    Pure tournament director: state + command + now -> state + events. (W1)
apps/server            Node + Socket.IO + Postgres. Table runtime, persistence,
                       identity, scheduler, tournament adapter.      (Workstream 0, W1 adapter)
apps/web               React client. Event-driven store, table, panels.  (Workstream 0 shell, W4 polish)
```

## Hard rules

- Chips are integers in the table's smallest unit. Cents mode is formatting only.
- Engine and tournament state is plain JSON. It is snapshotted to Postgres and must survive a restart.
- Cards are 2-character strings: rank `23456789TJQKA`, suit `cdhs` (e.g. `As`, `Td`).
- The server is authoritative. Clients send intents and get back views filtered per viewer.
- Hidden information never leaves the server unfiltered: every hole card goes through `visibleEvents`/views.
- Randomness: each hand's deck comes from its fairness seeds (rsdp-fair-v1, see [FAIRNESS.md](FAIRNESS.md)): a server seed from the runtime's random source, committed one hand ahead, mixed with the seated players' browser seeds. The runtime passes the full deck order into the hand. Tournament seat draws (rsdp-seats-v1, `seatRng` in `packages/tournament/src/seating.ts`) read a SHA-256 counter-mode stream from a secret 32-byte seed the manager makes for each tournament with `crypto.randomBytes` (`TournamentState.seatRng`: the seed and how many 32-bit words have been read, so a later draw carries on from there). `view()` never sends it, and nothing publishes it. Whenever `adopt` loads a tournament whose seats are still to draw from storage, it gives it a fresh seed and `rng` (`needsSeatSeed`, `withSeatSeed`; one the manager has just made keeps its own until it is loaded again): that upgrades a state saved before rsdp-seats-v1 (only the old mulberry32 `rng`), and retires a seed that a server rolled back to before rsdp-seats-v1 may have shown, since such a server sends `seatRng` to browsers. Once seats are drawn, the seed and its place are kept. The director keeps mulberry32 for any state that never got a seed. A new state's `rng` is never drawn from, but holds a second secret made apart from the seed (`CreateInput.legacyRng`, `crypto.randomBytes(4)`), so that a rolled-back server, which draws only from `rng`, draws from a secret its viewers are never sent. Tests inject a seeded random source.
- No PokerNow code, art, sounds or wording. Behaviour reference only.

## The hand engine (packages/engine/src/core)

Contracts: [`core/types.ts`](../packages/engine/src/core/types.ts) and [`core/api.ts`](../packages/engine/src/core/api.ts).

- The runtime builds a `HandInput` per hand: game spec, betting structure, stakes, seats dealt in, button (or dead button), planned forced bets, deck order and options (boards, bomb pot, run it twice).
- `startHand` returns a `HandState`. The runtime then calls `act`, `draw`, `voteRunItTwice`, `show`, `timeout` and `foldOutOfTurn`, and reads new `HandEvent`s from `state.events`.
- Settlement runs pot, then run (run it twice), then board (double board), then `awardPortion` from the variants package (high, low, hi-lo halves). Odd chips go to the first eligible seat clockwise from the button; in hi-lo the odd chip goes to the high half.
- `Modifier`s plug in before the hand (`beforeHand`), at pot award (`potFee`), after settlement (`afterSettle`), and after a post-hand show (`afterShow`, for claims such as the 7-2 bounty), so paid-feature modules never edit the core.
- `import '@rsdp/engine/modifiers'` registers every modifier's settings section and engine hooks. The server runtime and the web settings dialog both import it, so they parse the same `settings.modifiers` sections. Bomb pots have no engine hook: the runtime decides them between hands (`bombPotDue`), because their posts replace the blinds. A bomb pot takes no blinds: owed blinds stay owed, and the blind positions still move on one seat.
- Showdown: `HandOptions.showdown` is 'muck-losers' (last aggressor shows first, a hand shows only if it wins chips or beats or ties what is already shown) or 'show-all' (the table setting `play.revealAllAtShowdown`). Absent means show-all, so older stored hands replay unchanged.
- Betting structures: no-limit, pot-limit and fixed-limit share one `LegalActions` shape. Fixed-limit uses `smallBet`/`bigBet` per street and a raise cap.

## Table runtime (apps/server)

- One runtime per table. It owns the seat state machine (requested, approved, active, away, busted, leaving), the between-hands pipeline, timers, and permissions.
- Between hands, in this order: apply queued changes (settings, stack edits, rebuys, removals, approvals, moves), handle busts, check stop or pause, check the gate (`tableGate` for tournament tables), plan forced bets, shuffle, start the hand.
- Moves carry the turn they were pressed on (`TurnKey` in wire.ts): `hand:act`, `hand:draw` and `hand:timeBank` send `{ handNumber, at }`, where `at` is `view.hand.events.length` (the server's own `hand.events.length`: `visibleEvents` hides cards but never drops an event), and `hand:show` sends the hand number only. `hand:runItTwice` sends the hand number only too (each vote adds an event), and `voteRunItTwice` ignores a vote for another hand the same way it ignores one that lands after its vote closed, so a late vote never counts in a later hand's vote. `TableRuntime.checkTurn` refuses a seated player's move whose turn has passed, before the move itself is checked, so a tap that arrives after its turn (on a slow connection, usually the second of two) is never played on a later street. It skips anyone without a seat: a spectator may watch the table running behind, and the answer must not tell them where the live hand is. Without them (an older page, tests, scripts) a move counts for the turn now.
- Settings are one typed, versioned schema (zod) shared with the web. Edits queue and apply at the next hand. Every change is logged as a diff with who made it.
- Storage: Postgres via Drizzle when `DATABASE_URL` is set; otherwise embedded PGlite, which the live site runs on its Fly volume, and which development and most tests use. Two PGlite versions ship for now (D32): a folder in Postgres 18's format opens with PGlite 0.5; new folders, in-memory databases and Postgres 16 folders open with PGlite 0.2, which is what the live site's folder is in until it moves (#367); a folder from any other Postgres version is refused. CI also runs a small set of Postgres tests against a real Postgres (`TEST_DATABASE_URL`): `apps/server/test/postgres.test.ts` (migrations, storage round-trips, jobs, backup and restore) and the Postgres case of `migrations.test.ts` (upgrading a database with data in it); everything else uses PGlite. A durable job table backs every timer that must survive a restart (tournament auto-start, recurring events, waitlist offers).
- The cash ledger (what each player brought to a table, buy-ins, rebuys and host top-ups together, and what they took away) lives in the table's saved state: `state.ledger` (`LedgerRow`, `apps/server/src/runtime/types.ts`), stored in `table_snapshots.state` with the rest of the table. The Ledger tab, settle-up and its CSV read it there, and so do the leaderboard, profile history and profit graph (`tableNets` in `db/analytics.ts`, `db/history.ts`). The public record logs every change to a player's two totals (`chips` entries, `apps/server/src/audit.ts`), which is how players can check it. There is no ledger table: `chip_movements` and `seat_sessions`, made by the first migrations for a ledger that was never built, were never written to, and migration 0017 drops each of them where it is empty (`seat_sessions` only once `chip_movements` has gone, since one points at the other). One with rows would stay, unused.
- Identity: a persistent guest id per browser (localStorage `rsdp.guestId`); guests need no account for anything, tournaments included. Optional username and password accounts (`apps/server/src/accounts.ts`, `/api/account/*`, pages `/signin` `/signup` `/reset` `/profile`):
  - Signing up turns the browser's guest player into the account's primary player, so nothing moves.
  - Signing in elsewhere sends a session token (localStorage `rsdp.session`, socket auth `session`, header `X-Session-Token`); that browser plays as the primary player. When the player ticks "this is my device" (on by default; untick on a friend's phone), its guest id is linked to the account (its tables and tournaments show in the profile history) and its notes and picture are copied over (`adoptGuest`). Signing in while signed in to another account is refused. So is signing in (password, or Google to an existing account) while the browser's guest holds a seat, a seat request, a waitlist place or a seat held from the waitlist at a cash table, loaded or put away, or an entry in a tournament that isn't over (`AccountHooks.heldBy`): those can't move to another player id, so the player is asked to leave or unregister first, with a link to that table or tournament (`href` in the 409).
  - Signing out deletes the session and the browser's guest secret, so the browser starts over as a new guest. The web app turns alerts off first (`turnOffAlerts` in notify.ts), so the browser's push subscription goes too.
  - Passwords are scrypt hashes; sign-in pauses after 10 wrong passwords per address (and per username from that address) in 15 minutes. A password change or reset ends the other sessions, forgets the browser secrets of the account's players (the changing device excepted) and drops their open connections; the web app reloads when the server drops it. No email: the ADMIN_KEY holder makes a one-time reset code on /roadmap/admin (24 hours, stored hashed), which ends every session when used.
  - Sign in with Google (`apps/server/src/google.ts`): OpenID Connect code flow with PKCE, scope `openid profile` (no email kept), tied to the browser that started it. `POST /api/auth/google/begin` (mode signin, link or confirm) returns Google's address and sets an HttpOnly cookie; `/auth/google/callback` needs that cookie, checks the ID token and sends the page to `/auth/done#ticket=…`; `POST /api/auth/google/finish` needs the cookie, the same guest secret and (link, confirm) the same signed-in account before it signs in, makes the account (playing as the browser's guest when it has no account) or links Google. `accounts.google_sub` (unique; never swapped while linked) and `accounts.has_password` (false for Google-made accounts until a password is set). A Google-only account confirms with Google (a fresh Google login, max_age 300; one change, within 5 minutes, on that browser) before setting its first password or deleting itself. Linking and unlinking Google need the password on accounts that have one; an admin password reset unlinks Google. On only when GOOGLE_CLIENT_ID and GOOGLE_CLIENT_SECRET are set (deploy.yml copies the repository secrets to Fly; the redirect address is PUBLIC_URL from fly.toml + `/auth/google/callback`); otherwise `/api/auth/config` says off and the buttons are hidden.
  - Saved setups (cash table presets and tournament structures, table `saved_setups`, socket `setups:*`) live on the account for signed-in players and in localStorage for guests (`rsdp.presets`, `rsdp.tournamentStructures`). When a browser is signed in, the web client sends its local ones with `setups:import` (a taken name gets " (2)") and clears them. Up to 100 of each kind.
  - Deleting an account wipes the name, picture, notes, saved setups, secrets, sessions and push subscriptions of every player it owned; hands stay in history under the names used then.
  - On request, the operator replaces a deleted account's or a guest's name with "Deleted player" in old records (`apps/server/src/replaceName.ts`, `POST /api/admin/players/:id/replace-name` with the admin key, run from `replace-name.yml`; steps in [RUNBOOK.md](RUNBOOK.md#someone-asks-for-their-name-to-be-taken-out)). One transaction over table snapshots, table log and chat, tournaments and their lobby log, shared hands, feedback and the player's own name; a dry run (the default) only counts. Names beside the player's id go by the id. Only where their id is found, lines with no id (table log, the dealer's chat lines) are matched by the names the player used, as whole words, keeping longer names that contain one whole, and never inside a "Deleted player" already there; lobby events, whose fields hold a name whole, are matched exactly, and a Dealer's choice pick's chooser (`choice.current.by`, `choice.next.by`) goes by the chooser's id kept with it (`byId`, never sent to browsers); a pick saved before that id was kept is matched by name too, unless a practice bot made it or someone else of that name sits in its seat. A name is looked for inside a line of text only if it has a letter, at least two characters and a word outside `SERVER_WORDS` (every word of the server's own log and dealer lines; a test reads them from the code), so a name like "100" or "Game" never rewrites an amount or the server's wording; the report counts such names (`namesNotSearched`). Tables and tournaments are found by the player's id, so one where only their name is left (a declined seat request, a waitlist left, a tournament they unregistered from) keeps it. Hands and the public record hold no names and are never touched. It refuses an account that still exists, any table or tournament held in memory that the change would touch (its next save would undo it), and any run once the server has started shutting down (which waits for a change still running before its final saves); a `LoadGate` makes a table or tournament read from the database during the change read again before it is taken into memory. A change is an `admin` entry, `replace-name`, with `subjectRef('player', id)`.

## Players at the table (pictures, moods, gestures)

- A player's picture is per player, not per seat: `avatar:set` stores a library id (`AVATARS` in wire.ts) or a small uploaded data: URL in `player_avatars`. Seats show it as `SeatView.avatar`: `lib:<id>`, or `up:<version>` for an upload served at `GET /api/avatars/:playerId` (cacheable; a new upload is a new version). The server keeps a playerId → token map in memory and loads missing ones when a table is shown.
- `SeatView.mood` is an emoji kept on the seat (`seat:prefs { mood }`). Gestures are not stored: `table:gesture { to, kind }` is checked (host switch `chat.gestures`, target seated, a few per 10 s per tab) and relayed to everyone with the table open.
- Per-viewer choices (chips or big blinds on the felt, table sounds, chat beep, gesture visibility, hiding pictures and moods, keeping the screen on) live in `rsdp.prefs` with the look prefs.
- Practice bots (cash tables): `addBot`/`removeBot` on the runtime (`bot:add`, `bot:remove` sockets). A bot is a seat whose player id is in `state.bots` (owner, buy-in, look). Each bot takes the first of `BOT_LOOKS` (`@rsdp/engine/wire`: a short name, a colour and a robot face) that no other bot at the table has and whose name nobody there uses (seats, requests, waitlist, or anyone in the ledger), so bots are easy to tell apart. A person who sits down under a bot's name (a bot here, waiting, or gone but still in the ledger) keeps it, and the bot takes another (`giveWayTo`); only sitting down does this, so a seat request that is never approved renames nobody. A bot's ledger row keeps its owner and look, so hand records (`HandRecordView.seats[].bot`) still show its robot in replays after it leaves. Bots saved without a look get one when the table resumes. It counts as always online, can never be host, rebuys for its buy-in when it busts (or leaves when rebuys are off), and acts a moment after its turn starts through the `bot` timer. Its play lives in `apps/server/src/bots/strategy.ts`: Monte Carlo equity against random hands with the variant evaluators, using only what its seat can see, then pot-odds betting; draw games try every discard set. Each bot has a level (`BotInfo.level`, `BOT_LEVELS`: easy, normal, hard; missing means normal), picked with `bot:add`, `practice.level` or changed with `bot:level` (owner or staff with the players power). Easy calls small bets loosely, bets only good hands and small, and never bluffs. Hard thinks half again as long (twice as long about draws), deals an opponent who has bet, raised or called later streets extra random hands and plays the best of them (`handReads`, `readHands`), trusting those signals less for a player who bets most of the time. In 2-7 and Badugi it replays each opponent's draws, keeping what a player who threw that many cards would keep (`replayDraws`; a stand-pat the engine made for an away or timed-out player, `auto` on the draw event, says nothing), picks its own draw against the most dangerous opponents wherever they sit (`drawField`) and sizes up its bets with draws to come against all of them, and weighs only keeping its best few cards, plus the soundest set of that size when the lowest cards clash in Badugi or a straight or flush would spoil a 2-7 draw (`keepOptions`, `soundestKeep`): weighing every way to draw on a few deals each measured worse, since a lucky-looking bad draw wins more often. It learns each player's aggression and fold rate from the table's kept hands (`readPlayers` over `state.history`), bets thinner against callers, bluffs players who fold often, and calls wider in position. Bot ledger rows are flagged `bot`: the ledger shows them tagged, and settle-up pays only between people and says what the bots won or lost. A cash table with bots deals only while at least one person is dealt in. The host can stop players adding bots with `seating.allowPlayerBots`. `table:create` with `practice: { name, bots }` seats the creator and adds the bots; the first deal waits until the creator joins the table. Tournaments refuse bots (`addBot` throws).
- Coach tips and bot reasons (practice only): at the deal, `dealHand` sets `state.coach` (`{ handNumber, person, notes }`) when `soloPersonOf(hand)` finds exactly one person dealt in and every other dealt-in id in `state.bots` (membership, never the `bot-` prefix), on a cash table that has never dealt a hand between two people (`state.realGame`, set at the deal by `state.bots` membership too); otherwise it is null, and it fails closed (a forgotten bot counts as a person, a snapshot restored mid-hand without it gets nothing). `hand:tip { handNumber, at }` (`TableRuntime.coachTip`) checks all of that again, then the seat, the turn and the exact decision, and works the tip out in `apps/server/src/bots/coach.ts` from `seenBy(hand, seat)`: a `Seen` copy holding only what that seat can see (no deck, other hole cards, muck or seeds), the only type the coach accepts. It runs Normal's own `decide()` (exported as `normalDecide`) with dice that never bluff (`tipDice`) on its own random stream, seeded from the turn key and the player (`TipJob.seed`), so the table's `rng`, the deal and the bots are untouched, and the same spot gets the same random numbers on any thread. The work happens off the event loop, on the coach's own worker thread (`apps/server/src/bots/coachWorker.ts`, Node's `worker_threads`), so tips never hold up a table. `coachTip` makes every check on the table's thread and throws a refusal at once; only then does a `TipJob` (the `Seen` copy, the seat, the legal actions, the most cards to draw, the seed and the turn) cross to the thread, and the tip comes back as a promise. The server starts one thread with the first tip anyone asks for (lowered to nice 10 on Linux, so it gives way to the tables; 128 MB heap). A few tips may wait in line for it (8); one past that, or one that has waited 4 s, gets "the coach is busy, try again in a moment". A tip that runs past 3 s, or a thread that crashes, stops that thread: its tip gets the same message and a fresh thread starts. A thread that can't start turns away whoever is waiting, and the next tip tries again, so it is never started over and over. A tip that throws (a bug) fails as any handler does. The thread is started from `coachThread.mjs`, plain JavaScript that loads tsx itself (it gets none of the server's own flags), so it works under `npm run dev`, vitest and the production image alike; `createApp` stops it on `close()`. Tests of one table work tips out in-thread (`inThreadTips`, the `RuntimeDeps.tips` default). The ways to draw (and a bet with draws to come) always get every deal, with no clock, so a draw tip is the same for the same spot on any thread; a bet tip's equity still stops by about 120 ms so the answer is quick, so its numbers can differ slightly between asks (a turn's tip is cached, so only an ask after a restart, or after the coach was busy, works it out again). `tipLimits` in app.ts allows 10 worked-out tips per 20 s per player (a cached repeat, or a second ask while the first is being worked out, doesn't count, and one the coach was too busy to answer is handed back). Tips turned away for a full line or a long wait are counted and logged at most once an hour. The tip goes back on the ack alone, is cached in memory for that turn, and is never broadcast, logged or saved; `TableView.tips` only shows or hides the button. Bots move through `explainMove`, which returns the move with its `MoveWhy`; while `state.coach` is set, `botMove` turns that into a `BotNote` after the move is in, outside its try (a fault there loses the note, never the move) (`apps/server/src/bots/reasons.ts`: numbers and closed word lists, no cards, no discard positions, nothing about another person) on `state.coach.notes`, never in `hand.events`, so `visibleEvents`, `verifyHand` and the audit digest don't change. `finishHand` copies them to `HandRecord.coach` (in memory and the table snapshot, the last 30 hands; never the `hands` table), and `handRecordView(..., { notes: true })` serves them as `botNotes` to that one person only, from `table:history` and `table:export`; share links, `table:fullLog` and hand search never ask for them.

## Tournament integration (packages/tournament <-> apps/server)

- The director is pure: `apply(state, command, now)` and `tick(state, now)` return `{ state, events }`. `nextWakeAt(state)` tells the scheduler when to call `tick`.
- The server translates socket calls into commands, runs the hands, and reports each hand's `startStacks`, `endStacks` and knockouts per table.
- Before dealing on a tournament table, the runtime asks `tableGate(state, tableId, now)` and reads `levelFor(state, tableId)` for game and blinds.
- Director events such as `moveSeat` and `tableBroken` are applied between hands.
- The lobby's Activity tab: `logEvent` (`packages/tournament/src/log.ts`) turns each director event into a public `LogEvent` (names, never player ids), which the server saves with the lobby chat, or leaves it out. It names every kind of event, the ones left out included, with no catch-all, so a new kind fails to compile until someone decides whether the lobby sees it. `logText` (`apps/web/src/tournament/logText.ts`) words each `LogEvent` under the same check; an older open tab shows nothing for a kind it doesn't know. A host settings change is logged with the names of the settings that changed (`settingsUpdated.changed`), and a save that changed nothing isn't logged; the tab folds changes less than 5 minutes apart, with nothing else between them, into one line.
- Host and co-hosts: `@rsdp/engine/roles` is the one co-host model for cash tables and tournaments. A host names co-hosts and gives each some powers (`approve`, `chips`, `run`, `players`, `settings`); managing co-hosts, handing over the host role and archiving stay with the host. Tournaments keep them in `state.coHosts`; the server checks every staff command with `mayCommand(state, playerId, command)` from `@rsdp/tournament` before the director sees it.
- Lobby chat moderation is not a director command, since the lobby chat stays open after the event ends (when the director takes no more commands). The manager keeps it in `state.lobbyChat` (`off`, `muted`; optional, so older saves load) with `muteInChat` and `setChatOff`, and the server refuses a lobby message with `lobbyChatRefusal`. Who may do it is `chatModerationRefusal`: the host and co-hosts with `CHAT_POWER` (`players`, the power that mutes at a cash table), and only the host acts on the host or a co-host (so a muted player handed the host role is taken off the mute list, and a co-host can't unmute themselves). `viewFor` sends the mute list only to them; anyone else sees only themselves on it. `tournament:chatDelete` finds the message in the lobby list in memory or, if it is older than that list's newest 300, in `tournament_log`; it deletes the row (after its own save), then drops it from the lobby list in memory and sends `tournament:chatDeleted` to everyone watching; browsers remember deleted ids, so a full list that crossed the deletion doesn't bring it back, and the full list sent after a reconnect replaces everything but what was appended since (so a message deleted while offline goes too). Hiding someone just for yourself is the tables' list in the browser (`apps/web/src/chatMutes.ts`, by player id).
- Host tools in the director: `approve` takes an optional `stack` (a handicap), `setStack` (waits for the player's hand to end; not a rebuy), `movePlayer` (between hands; a taken seat swaps the two players), `archive` (`state.archivedAt`; before the start it also cancels). Lists should skip archived events. The server's hourly cleanup archives manual and Sit & Go events left untouched for 30 days and drops finished events from memory an hour after they end; results are never deleted.
- After a crash, a table saved behind its director is brought in line (`alignTables` in the manager): a hand the director already closed is dropped rather than played again, and a hand the director heard start but the table never saved is closed with no chips moving. The director also ignores a result for a hand it has already closed.

## Phone alerts (apps/server/src/push, apps/web/public/sw.js)

- Four alerts: a registered tournament starting in 5 minutes, being seated when the cards are drawn, being moved to another table, and your turn (to bet or draw, or a Dealer's choice pick the table is waiting for: "Your pick"). An open tab shows them while it is in the background (`notify` in `apps/web/src/notify.ts`, through the service worker's `showNotification`, so Android Chrome works); with alerts on, the browser is also subscribed for Web Push and the server sends the same alerts to it, so they reach a locked phone or a closed site. Off until the player turns them on (the browser asks permission then); the choice is per browser (`rsdp.notify`). Safari on iPhone and iPad has alerts only for a site added to the home screen and opened from there, so the button explains that instead (`install` state).
- One alert per device: the page and the push use the same tag (`turn:<table>:<hand>:<events.length>`, `turn:<table>:pick:<hand it follows>`, `seat:<tournament>:<table>`, `start:<tournament>:<startAt>`). The page skips an alert already showing; `sw.js` shows a push whose tag is already showing quietly (`renotify` false) and closes the alerts it `replaces` (an earlier turn or pick at the same table, the alert for an earlier seat in the same tournament, so a tap never opens a table the player has left). Acting or picking at a table, or its clock running out, closes that table's turn alerts only. Coming back to a tab closes the alerts that tab raised and any whose page is the one on screen; the rest stay (a turn at another table still needs its player). Tapping one opens its page: `notificationclick` focuses a tab already there, else tells an open tab to go there (`{ open }` message, a `pushState` navigation), else opens a window. Both sides resolve the page against the site's own origin and drop anything that would leave it. Starting soon in an open tab (`TournamentAlerts.tsx`) waits while the event's lobby or one of its tables is on screen in any tab (each tab notes it in `rsdp.notified.onScreen`, for 35 s), and comes when the player looks away. `sw.js` notes the tag of each alert it showed in cache storage (`rsdp-alerts-shown`, the newest 50), and the page doesn't give one a push already showed on this device (`shownByPush`). An alert counts as given (`rsdp.notified`) only once `notify` says it is on the device, so a tab that closes as it looks away leaves it to another tab or the next visit. A tab claims each one it is about to raise (`rsdp.notified.raising`, lapsing after 10 s) before it waits on that record, so two tabs checking at once (the player switching from the lobby's tab to another) raise it once.
- Sending (`apps/server/src/push/webpush.ts`): our own RFC 8291 encryption (aes128gcm, one record) and RFC 8292 VAPID (ES256 JWT, `vapid t=…, k=…`) on node:crypto, checked against the RFCs' examples in `test/push-crypto.test.ts`: the encrypted message byte for byte, the VAPID header and claims byte for byte, and the signature by verifying it (ECDSA signatures are random, so no two match). Only to the push services of Google (fcm.googleapis.com, android.googleapis.com), Mozilla, Apple and Microsoft (`pushService`), over https on the default port with redirects refused, so a subscription can't make the server call anything else. A short TTL (60 s for a turn, 5 minutes for a seat, until the start for starting soon), urgency high except for starting soon, 5 s per request. A 404 or 410 drops the subscription; other failures are logged, at most once per 10 minutes and without the address.
- `PushAlerts` (`apps/server/src/push/alerts.ts`) never holds up the game: `send` queues the alert and returns, at most 4 requests run at once and the queue holds 500. A turn alert carries a check that it is still that turn and nobody is looking, asked again as it leaves the queue, so one held up behind a slow push service is dropped rather than sent late. On only when `PUBLIC_URL` is set (it is the VAPID contact), so a copy, the restore drill on real backups and the dev server send nothing; `GET /api/push/key` then answers `{ key: null }` and the page offers open-tab alerts only.
- Routes: `GET /api/push/key` (the VAPID public key), `POST /api/push/subscribe` (the browser's `PushSubscription` JSON, with `X-Guest-Token` and `X-Session-Token` as the account routes take them; on every page load while alerts are on, from `syncPush`, which also resubscribes when the server's key changed; the alerts button says they also come with the site closed only while the browser has push and the last `syncPush` didn't fail) and `POST /api/push/unsubscribe { endpoint }`. 60 calls per 10 minutes per address.
- Storage: `push_keys` holds the VAPID key pair (one `vapid` row, made on first use, so it is in the locked backups and a restore keeps everyone's subscriptions working). `push_subscriptions` is keyed by endpoint: the player it alerts, the browser's `player_tokens.token_hash` (`device`, cascades when the secret is forgotten), the session's hash when signed in, the browser's keys, and `seen_at`. A subscription counts only while that browser would still play as its player (`pushTargetsOf`: the device's token is that player's, or its session is live and its account's primary player is that player), so signing in on a friend's phone stops alerting once the session ends. At most 10 per player (the newest kept). `prunePushSubscriptions` runs at start and every 6 hours, forgetting the invalid ones and those not seen for 60 days.
- When: your turn is noticed as each table broadcasts (`watchTurn` in app.ts), once per turn (`turnSeen`, keyed by `turnToAct`'s `key`: player, hand, events so far; for a pick, player and the hand it follows, so a pause and its fresh pick clock don't make a new one; nor does a pick clock started again after the host stops the game between hands, so a player away from the site isn't told again, though an open tab does alert again), and sent 2 s later (`TURN_ALERT_DELAY_MS`) only if it is still that turn and none of the player's tabs at that table is on screen; a paused table holds it until it resumes. Tabs report `page:visible { visible }` on connecting and when the page is shown or hidden; a tab that never says counts as on screen. Seated and moved come from the tournament manager's `onMoved` and skip a player with any tab of the site on screen. After a restart (`resume`), turn and seat alerts due in the first 10 s (`RESTART_QUIET_MS`) wait until then, so tabs can reconnect and say whether they are on screen first, and a seat the manager only puts back at a table saved behind the director (`reconcileSeats`, `restored`) sends none: the player heard of it before the restart. Starting soon is `StartAlerts` (`apps/server/src/push/starts.ts`): a timer per tournament that is registering or seating, 5 minutes before `startAt` to every entry still in, once per start time, re-armed when the server starts.
- Payloads hold only the title, a short body (the table or tournament name, minutes to start), the page and the tag: no cards, stacks or amounts.

## Database migrations (apps/server/drizzle)

- `apps/server/src/db/schema.ts` describes the tables; the migrations are the numbered SQL files made from it, listed in order in `meta/_journal.json`. The server applies the pending ones at start-up (`createDb`), on Postgres and PGlite alike.
- To change the database: edit schema.ts, then from the repo root `npm run db:generate` writes the next migration and `npm run db:check` checks the migration files agree with each other. CI fails when schema.ts has a change no migration covers (it compares schema.ts with the snapshots in `meta/`, not with the SQL). `apps/server/test/migrations.test.ts` checks that the SQL builds the tables schema.ts describes (columns, defaults, indexes and constraints, so a hand edit that changes one of them fails it), checks the journal, and upgrades a database that has data in it from the migration before the newest.
- Additive and idempotent only: new tables, new columns (nullable or with a default), new indexes and constraints, each safe to run twice (`IF NOT EXISTS`, or a `DO` block that ignores `duplicate_object`). drizzle-kit 0.31 writes neither, so add them to the generated SQL before it ships. The code before the change must still run on the new schema, because a revert runs it there.
- A drop or rename takes two releases: the first stops using the old column or table (a rename adds the new one and copies the data across), and a later release drops it, once no release we might go back to still reads it.
- A drop never deletes rows. drizzle-kit writes `DROP TABLE … CASCADE`: replace it with a `DO` block that drops the table only if it is empty and leaves one with rows in place, safe to run twice (see `0017_drop_unused_ledger.sql`), and the code must work either way. Older backups still list the table, so add it to `RETIRED` in `db/backup.ts`: a restore makes it again for their rows, then runs the drop again.
- A revert keeps the migration files. Databases that ran a migration keep its changes, so reverting code never deletes a migration or its journal entry, and what it added stays in schema.ts too (or `db:generate` would write a migration dropping it, and CI fails); undo a change with a new migration.
- Never edit a migration that has shipped: a database that ran it never runs it again, so the edit would reach only new databases. Write a new migration.
- Each journal entry's `"when"` must be newer than every earlier entry's. Drizzle runs only the entries newer than the last one a database applied, and skips the others with no error, so a migration stamped older would never run in production (fresh test databases still run it). `db:generate` stamps the time it runs; never pick a number by hand. If develop gained a migration while yours waited, delete yours (the .sql file, its snapshot and its journal entry) and run `db:generate` again on top.
- A migration that rewrites existing rows (not just adds) also needs a step in `restoreBackup` (`db/backup.ts`), which loads older backups straight into the newest tables.
- Table and tournament state are JSON snapshots inside rows, so changing their shape needs no migration, but saved snapshots must stay readable: see the comments on `RUNTIME_VERSION` (`apps/server/src/runtime/types.ts`) and `STATE_VERSION` (`packages/tournament/src/types.ts`).

## Changing contracts

Changes to `core/types.ts`, `core/api.ts`, the settings schema layout, the event list, or the runtime/tournament integration need a short note to the other workstream threads before merging. If stored state changes shape, older snapshots must still load: new fields are optional and filled in on load. Bumping a snapshot version instead makes every saved table or tournament of the old version fail to load (see `RUNTIME_VERSION` in `apps/server/src/runtime/types.ts`).

## Fair dealing

Decks come from `deckFromSeed(handSeed)` (`@rsdp/engine`, `fairness.ts`), never
from `shuffle(freshDeck(), …)`. The runtime commits to each hand's server seed a
hand ahead (`view.fair.nextCommit`), seated browsers add seeds with `fair:seed`,
and `HandInput.fair` carries the record into history. `fair.serverSeed` and
`fair.handSeed` give away the whole deck: only `handRecordView` may show them,
and only once `fairRevealed()` says so. Every card-dealing event carries `pos`.
See docs/FAIRNESS.md.
